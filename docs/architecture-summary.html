TPCx-HS on a single node

A five-daemon pseudo-distributed Hadoop cluster on one ARM64 virtual machine, driven by the real TPCx-HS v2.0.3 kit. 1,000,000,000 bytes generated and verified in 28.4 seconds. A working architecture study — and, by construction, not a publishable benchmark result.

The five roles

Pseudo-distributed means every daemon is a separate JVM talking over loopback: the same code paths a real cluster uses, on one box. The cluster splits cleanly into a storage half and a compute half.

Daemon Layer Heap What it does during a TPCx-HS run
NameNode HDFS 512 MB Holds the namespace and block map in memory; decides which DataNode takes each 128 MB block. Never touches record data.
DataNode HDFS 256 MB Stores the blocks on the ext4 volume and serves them to tasks. The only daemon that moves bulk data.
SecondaryNameNode HDFS 256 MB Merges the edit log into fresh fsimage checkpoints. Not a hot standby — it exists so the edit log cannot grow without bound.
ResourceManager YARN 384 MB Cluster scheduler. Owns the whole container pool — 3840 MB and 4 vcores — and hands out leases.
NodeManager YARN 384 MB Launches and monitors containers, enforces their memory ceilings, and serves map output during a shuffle.
Heaps are set explicitly in hadoop-env.sh. Hadoop's default is 1 GB per daemon; five of those would exceed this VM's physical memory.

How HSGen writes a gigabyte

HSGen is the generation phase. The thing worth seeing is what is absent: no reduce stage, so no shuffle, so no intermediate copy on local disk.

The command that actually ran

Copied verbatim from the kit driver's own HSGen line (TPCx-HS-master.sh:232), with only the record count reduced:

hadoop jar TPCx-HS-master_MR2.jar HSGen \ -Dmapreduce.job.maps=4 -Dmapreduce.job.reduces=4 \ -Dmapred.map.tasks=4 -Dmapred.reduce.tasks=4 \ 10000000 /user/jiho/TPCx-HS-benchmark/HSsort-input
 A TPCx-HS record is 100 bytes — KEY_LENGTH 10 + VALUE_LENGTH 90, from HSInputFormat.java:55-57 — so records = GB × 10,000,000.

Why the kit's own driver was bypassed

TPCx-HS-master.sh was read before being used, and four things ruled out running it as shipped:

  • Its smallest scale factor is 100 GB. -g 1 means 109 records, and the guide itself calls that “for test purpose only, not a valid Scale Factor”. This VM has ~10 GB of HDFS capacity, so no -g option fits.
  • It runs the full suite twice — HSGen, HSSort, HSValidate, looped — which is Milestone 3's job, not Milestone 2's.
  • It deletes data without asking. Every run opens with hadoop fs -rm -r -skipTrash over the benchmark directory.
  • It needs sudo, which requires a password here.

Calling the kit's HSGen class directly keeps the exact benchmark code path while staying inside the milestone and inside the disk budget.

Three decisions worth defending

Each came out of a failure that had to be diagnosed, not from a tutorial.

The NameNode runs on port 8020, not 9000

The kit's HSDataCheck class hardcodes its own NameNode address — conf.set("fs.defaultFS", "hdfs://127.0.0.1:8020" + args[0]) at HSDataCheck.java:34. On port 9000 it died with ConnectException while the shell version of the same check passed. Port 8020 is Hadoop's own default anyway, so matching it fixes the kit's tool without editing kit source — which keeps the run traceable to an unmodified kit.

The SecondaryNameNode address is pinned explicitly

Left at its 0.0.0.0 default, start-dfs.sh rewrites the address to the output of hostname and then SSHes there. Only localhost was authorised, so the daemon silently never started and jps showed four of five. Pinning it to localhost:9868 makes startup deterministic.

Virtual-memory checking is off

The JVM reserves a large virtual address space on aarch64, and YARN's default 2.1× vmem ratio kills containers that are perfectly healthy. Physical-memory enforcement stays on, so containers remain bounded — just by the limit that means something on this architecture.

Why the data can be checked without trusting the run

HSGen's output is a deterministic function of the record number (Random16.skipAhead(rowId)), so the kit's GenSort compiles standalone and rebuilds any slice of the dataset outside Hadoop. Records 0–4 regenerated that way are byte-identical to what HDFS holds, and re-running the generator over all 10,000,000 records reproduces the checksum 0x4c49607ac53602 — the same 21472776955442690 that HSGen's own counter reported. The value Milestone 3 validates against is therefore confirmed independently of the MapReduce job that produced it.

One correction worth recording, because it is an easy thing to get wrong in a write-up: the JimGrayRIP string visible at the start of the first record is not a marker the kit stamps in — grep -i 'jim\|gray\|RIP' over the kit sources finds nothing. It is the computed 10-byte key of record 0, the high 10 bytes of the 128-bit random value from Random16.skipAhead(0) (GenSort.java:43-45), followed by the recBuf[10]=0x00, recBuf[11]=0x11 break. It is evidence that the generator's sequence started where it should, not proof of provenance — TeraGen uses the same algorithm and emits the same bytes.

Where this departs from the specification

Not a publishable result

Two of the deviations below are structural and cannot be engineered away on one node, so no TPCx-HS performance metric (HSph@SF) is produced or claimed. Saying so plainly is part of the deliverable.

Spec requirementThis buildWhy
Replication factor ≥ 31 One node cannot hold three independent replicas. The headline non-compliance.
Scale factor ≥ 1 TB1 GB Three orders of magnitude below the smallest valid factor, and below the 100 GB the kit's driver even offers. Chosen to fit a 30 GB volume.
Multi-node clustersingle node No rack awareness, no cross-host shuffle, no node-failure behaviour to observe.
Cluster Validation Suiteskipped Needs clush/pdsh, meaningless on one node and requiring root to install.
Dedicated hardwareshared VM ~1.7 GB of RAM is held by the resident VS Code server, and at peak the daemons, container pool and server total ~7.3 GB of 7.7 GiB. Sort timings will be pessimistic.
 What remains valid is the architecture and the functional correctness of the data path — which is what Milestones 2 and 3 ask for.

Handing over to Milestone 3

The 1 GB dataset is in place. Check jps first, because the cluster may be down. These steps are a real sequence — each depends on the one before it.

  1. Bring the cluster up if it was stopped: ./scripts/03-start-cluster.sh. It waits for safe mode to clear and fails loudly if any daemon is missing.
  2. Decide the input size. 1 GB is in place; 2 GB is the comfortable choice and 3 GB is reachable. To change it, delete the existing dataset first — 05-hsgen.sh refuses to overwrite one — then ./scripts/05-hsgen.sh 2.
  3. Run HSSort with the kit's own command line from TPCx-HS-master.sh:265. Expect to tune NUM_REDUCERS: this is the memory-hungry phase and the one the VM is tight for. Reducers are 1024 MB, so at most 3 run at once beside the 768 MB ApplicationMaster.
  4. Run HSValidate and compare against the HSGen checksum above. The kit's USER_GUIDE.txt documents a known IndexOutOfBoundsException here (MAPREDUCE-6635) with specific map/reduce workarounds — though those assume a real cluster and will need rethinking on 4 vcores.
  5. Watch df -h / between phases. The 3× guard in 05-hsgen.sh does not cover a sort launched by hand.

Repository: ~/tpcxhs-m2 — README, Hadoop and kit configuration, and nine numbered scripts that rebuild this from a clean VM. Software lives in ~/opt/{java8,hadoop}, cluster state in ~/hadoop-data, and the kit stays unmodified at ~/project/TPCx-HS_Kit_v2.0.3.
